[2026-08-15] Language decision and MVP scaffold

Decision: TypeScript (rationale recorded in spec 33.1)
- A Rust core with napi-rs bindings was scaffolded and then withdrawn.
- Reasoning: the workload is I/O-bound (process stdout, WS fan-out, SQLite), and the 28.1 targets are met either way.
  Rust's real wins are idle memory (60-150MB down to 10-20MB) and distribution size (80-110MB down to 10-15MB).
  Against that: MCP SDK maturity, Embedded Mode (a 6-target napi build matrix), and MVP velocity.
- Reversible: chapters 16 and 17 are the language boundary, so replacing the core leaves runtime clients untouched.
  Three re-evaluation triggers are recorded in 33.1.

[2026-08-15] Bug hunt on the implemented surface

Method: read the code for defects, then proved each suspicion with a probe script against the built dist
before claiming it. Four real bugs found, all fixed, all covered by regression tests.

B1 (EventBus, root cause of three symptoms) - subscriptions were identified by the handler function
   reference: #handlers was a Set of functions and #scopes a Map keyed by function. Reusing one function
   for two subscriptions collapsed them.
   - onSession("s1",h) then onSession("s2",h): the first subscription silently became s2-scoped.
   - on("message",h) then onSession("s1","tool_call",h): the global subscription stopped firing entirely.
   - unsubscribing one of the two removed both.
   Attaching one logger to several sessions is ordinary usage, so this would surface immediately.
   Fix: each subscribe() creates its own Subscription object holding {handler, scope, active}.

B2 (EventBus) - a nested emit() from inside a handler was delivered depth-first, so subscribers observed
   seq 99 before seq 1 finished. Spec 15.3 makes per-session ordering a MUST, and the Session Manager will
   emit from handlers. Fix: emit() queues and drains, so nested events dispatch after the current one.

B3 (ProviderManager) - concurrent detect() calls for one id all missed the cache and each ran the adapter.
   With real adapters that means duplicate process spawns. Fix: in-flight promises are shared per id.

B4 (ProviderManager) - a failed detection was cached for the full 60s TTL, so installing a CLI mid-session
   stayed invisible for a minute. Fix: separate failedDetectionTtlMs (default 5s) from the success TTL.

Also corrected: register() threw AB-1001 ("Unknown provider id") for a duplicate id, which is the wrong
code. Added AB-1007 "Duplicate provider id at registration" to the spec table and ERROR_CODES (now 40).

[2026-08-15] Storage decision: no database in the MVP

Dropped SQLite. Measured against what is actually stored - tens of sessions, tens of MCP servers,
hundreds of permission rules, thousands of monthly approval records - a relational engine buys nothing.
The one workload that would justify it is a persisted event log, but events already live in the
per-session memory ring buffer for reconnect replay, and the persisted copy is only for audit.
Dropping it removes a database, a migration system, and a native dependency from the critical path.

Chapter 20 rewritten around a Storage interface with memory and file backends, atomic
write-and-rename durability, and quarantine instead of refusing to boot on a corrupt document.
Recorded as decision D10, with the trigger to revisit: persisted event history, several runtime
processes sharing state, or state files outgrowing full-file rewrites. At that point use node:sqlite,
built into Node 22+, so the dependency count stays at zero.

[2026-08-15] Wiring storage and logging into the managers

Storage was built and tested but nothing wrote to it, so spec 28.2's promise that a restart restores
session metadata was not true. Now:

- SessionManager persists on every mutation - create, stop, resume, updateMcp, setPermissionMode -
  and restores at start(). A restored session comes back "stopped" rather than pretending to be
  live, because its agent process is genuinely gone. What survives is the metadata and the
  provider's own session id, which is what makes resume() able to continue the conversation.
- McpManager persists registrations and reconnects them at start, attempting each independently so
  one server failing to come back leaves the others alone.
- PermissionManager persists rules, restores them at start (skipping any that no longer validate,
  loudly), and appends every decision to the audit trail.
- A storage failure never takes a live session down; it is logged and the session continues. Covered
  by a test that throws from put().

Verified by actually restarting the daemon rather than by unit test alone: run 1 creates a session
over HTTP and is killed; run 2 starts fresh against the same data dir and GET /sessions returns the
session with its title, working directory, and status "stopped".

Logging is now wired through the managers, so the spec 27.1 event list actually fires:
agent.started, runtime.listening, mcp.connected, mcp.reloaded, session.created, session.status,
session.stopped, permission.requested, permission.decided, and the *_failed variants.

Two things the log output itself exposed:
- The runtime credentials path was logged under the key "credentials" and redaction masked it. The

- session.stopped fired twice when a stopped session was stopped again during shutdown. stop() is

[2026-08-15] secret:// resolution

Implemented spec 26.3. A reference looks like `secret://<service>/<account>`, and resolution happens
at one seam per consumer: session env in SessionManager.create and resume, MCP env and headers in
McpManager.add. Resolvers ship for the OS credential store (shelling out to `security`,
`secret-tool`, or PowerShell so there is no native dependency), the environment, an in-memory map,
and a chain that takes the first hit.

The design decision that matters: an unresolved reference fails with AB-6004 rather than passing
through. Handing the literal `secret://...` to a child process looks like a real value, and the
failure then surfaces as an authentication error somewhere else entirely - hours of debugging for
what is really a missing keychain entry.

Three layers verified against the running daemon, because "the secret does not leak" is only worth
claiming if each layer is checked:
  API response     "DEMO_TOKEN": "***"
  state on disk    "DEMO_TOKEN": "secret://demo/token"
  process env      the resolved value
The manager keeps two copies: `config` as registered, which is what gets persisted, and
`runtimeConfig` with references expanded, which is never persisted and never returned.

[2026-08-15] The ask hook: approval that reaches an agent's own tool calls

Until now `ask` only covered calls the host made itself. An agent's own tool calls were settled by
the CLI's internal prompt, which in non-interactive mode denies - so a desktop app wanting an
approval dialog got nothing to show. That was the largest gap in the primary use case.

The mechanism was found rather than guessed: `--permission-prompt-tool` does not appear in
`claude --help`, but the binary carries it 19 times alongside `canUseTool` 139 times, and the strings
spell out the contract - "must be an MCP tool", "a tool_name+input wire", answered with
behavior:"allow" plus updatedInput, or behavior:"deny" plus a message.

The awkward part is that the CLI runs the prompt tool in its own process, so a decision has to cross
a process boundary to reach the host. Three pieces:
- ApprovalGateway: a loopback endpoint with a per-start token and exactly one route.
- bin/approval-mcp.mjs: a one-tool MCP server the CLI launches, forwarding to the gateway.
- The Claude adapter injects that server and passes --permission-prompt-tool.

Every failure path resolves to a denial, because the agent is blocked while it waits: an unreachable
gateway, a malformed request, a throwing host callback. A hang there would freeze the turn with no
way out. A tool the registry cannot resolve is treated as WRITE.

autoApprove(true) answers everything without asking. It installs a highest-priority allow rule
rather than a parallel switch, so it shows up in listPolicies() and is lifted the same way it was
set - a hidden boolean that silently allows everything is exactly the kind of thing that should be
visible.

Verified against the real CLI in all three modes:
  approve  prompts=1  file="approved write"
  deny     prompts=1  file="before"
  auto     prompts=0  file="approved write"

Spec 25.4 rewritten: it described this as a limitation, and now describes the mechanism.

[2026-08-15] Twelve packages became one

The split was wrong for consumers. Nobody installs a runtime without a provider, or an MCP manager
without its registry, so the boundaries asked for an install decision that carried no real choice -
and getting it wrong meant a missing import at runtime rather than a helpful error.

Now `@jeonhui/agentbridge` ships everything behind subpath exports, so the boundaries stay visible
where they help (in imports) and disappear where they did not (in installs):

  @jeonhui/agentbridge              core
  @jeonhui/agentbridge/claude       adapters
  @jeonhui/agentbridge/mcp          MCP manager
  @jeonhui/agentbridge/permission   policy and approvals
  @jeonhui/agentbridge/runtime      REST and WebSocket
  @jeonhui/agentbridge/sdk          one client over both transports

The CLI stays separate as @jeonhui/agentbridge-cli, since it is a binary rather than a library.

Internal module boundaries are unchanged: the directories under src/ are still what the dependency
rules in spec 8.4 govern, and cross-directory imports became relative paths rather than disappearing.

One thing worth keeping: the tests reached shared fixtures through a counted stack of `../`, which
broke the moment the layout moved. They now find the repository root by walking up until the
fixtures appear, so the next move will not touch them.

Verified after the merge: 285 tests, the MCP and integration checks, the tools example, the CLI, and
a single-package tarball installed into a scratch project and driven through every subpath.
112 kB, no test files.

[2026-08-15] Documentation sweep, and a real bug it uncovered

Asked whether the docs were all updated. Two were stale and one turned out to be a defect.

Stale:
- The MVP scope table in 29.1 still named packages/* directories that the consolidation removed.
  It now names src/* directories, and the permission row covers the prompt hook it gained.
- The package README shipped to npm with relative links. npm resolves those against the package
  directory, so the specification and licence links would have 404'd on the package page. They are
  absolute GitHub URLs now. The root README keeps relative links, which are correct on GitHub.

The defect: running the suite turned up 23 cancelled tests with
"Promise resolution is still pending but the event loop has already resolved". The approval timeout
timer was unref'd, so when nothing else held the loop open the process exited with the caller still
waiting - the exact hang that deny-on-timeout exists to prevent, arriving by another route. It had
been passing only because other tests in the same process kept the loop alive.

Audited every unref in the codebase against one rule: a timer that is the only thing able to settle
a promise is never unref'd. Four were wrong (approval timeout, the MCP server's send wait, provider
detection, MCP retry backoff); the rest are periodic or backed by a child process or server that
holds the loop open, and stay as they were. Recorded in spec 25.4.

[2026-08-16] DX audit: pretended to be a new developer, found three walls, removed them

Method: installed the published package into fresh projects and followed the README exactly - plain
ESM, TypeScript 7 with bundler resolution, CJS require, and the three most likely first mistakes.

Found and fixed, each verified against a packed tarball rather than the workspace:
1. TypeScript users without @types/node hit a wall of "Cannot find namespace 'NodeJS'" from our own
   .d.ts - and installing @types/node did not even help under TS 7. The real fix was not a
   dependency but restraint: the public surface no longer leaks NodeJS.Platform or NodeJS.Signals
   (now string and a self-contained ProcessSignal union). Zero type errors with zero @types.
2. The quickstart sprayed three JSON log lines to stderr, because the library defaulted to info.
   A library should be quiet; the daemon opts into info explicitly. Default is warn now.
3. The most common first error - forgetting registerProvider - said only "Unknown provider id".
   It now coaches: names the id, lists what is registered, and says what call is missing.

Also learned: CJS require() of this ESM package works on modern Node (require-esm landed in
20.19/22.12), and TS 7 has removed node10 resolution outright, so the legacy-tsconfig cohort breaks
on their own config before ever reaching our subpath exports.

0.1.3 ships these plus the rewritten README onto the npm page.

[2026-08-16] Host-app audit: bundlers and the browser

Asked whether other apps can import this easily, so other apps were simulated: an esbuild-bundled
host (the shape of an Electron main process or a packaged server), TypeScript under node16
resolution, a CJS host, and a browser page.

Found and fixed:
- Bundling broke on our own code. The permission prompt tool shipped as a file resolved with
  createRequire(import.meta.url) - import.meta is illegal in CJS output, and the resolved path
  points nowhere once code leaves node_modules. The tool is now dependency-free source (hand-rolled
  newline-delimited JSON-RPC, no MCP SDK) embedded as a string and written to a temp file at
  runtime, so it travels inside any bundle. Verified against the real CLI in all three ask modes.
  One trap inside the fix: the source crosses three escaping layers (writer -> TS template ->
  generated file), and a single \n became a real newline in the generated file, producing a syntax
  error. The handshake was tested by speaking MCP to the generated server directly before going
  near the real CLI again.
- /sdk could not bundle for the browser because it value-imported AgentBridgeError through the core
  barrel, dragging node:fs and node:child_process along. It now deep-imports the error class, and
  esbuild --platform=browser produces a ~13 kB bundle of the HTTP client.
- dist/testing (a test-only helper carrying import.meta) shipped for nothing; excluded.

Verified matrix, all from a packed tarball: CJS bundle runs as-is; single-file ESM runs with the
standard createRequire banner (a dependency uses dynamic require - esbuild limitation, documented);
browser bundle of /sdk builds clean; TypeScript node16 resolution has zero errors; the bundled host
generates the prompt tool from inside the bundle.

The web answer, recorded in the README: the runtime is Node-only by nature (it spawns CLIs and
reads keychains), but a web page bundles /sdk and talks to the local daemon over REST + WebSocket.

0.1.4 ships this plus a README Bundling section with the verified table.
